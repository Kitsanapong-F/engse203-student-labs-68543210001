## 1. ภาพรวม

วาดแผนภาพความสัมพันธ์ของ 2 ตาราง (ใช้ตัวอักษรวาดก็ได้) แล้วอธิบายว่าเป็นความสัมพันธ์แบบใด (หนึ่งต่อหนึ่ง หนึ่งต่อหลาย / หลายต่อหลาย)

```text
┌───────────────────────┐               ┌────────────────────────────────┐
│         users         │               │            requests            │
├───────────────────────┤               ├────────────────────────────────┤
│ PK  id (INTEGER)      │ 1 ──────────< │ PK  id (TEXT)                  │
│     name (TEXT)       │   │           │ FK  requester_id (INTEGER)     │
│     department (TEXT) │   │           │     request_type (TEXT)        │
│     email (TEXT)      │   │           │     location (TEXT)            │
└───────────────────────┘   │           │     details (TEXT)             │
                            │           │     priority (TEXT)            │
                            │           │     status (TEXT)              │
                            │           │     created_at (TEXT)          │
                            └─────────< │ FK  updated_by (INTEGER)       │
                                        │     updated_at (TEXT)          │
                                        └────────────────────────────────┘
```

**ประเภทความสัมพันธ์:** หนึ่งต่อหลาย (One-to-Many / 1:N)
* **ผู้สร้าง (requester_id):** User 1 คน สามารถสร้างได้หลาย Request
* **ผู้แก้ไข (updated_by):** User 1 คน สามารถแก้ไขได้หลาย Request

## 2. ทำไมต้องแยกเป็น 2 ตาราง

**ข้อนี้สำคัญที่สุด** — ผู้สอนจะอ่านข้อนี้เป็นหลัก
* ตอน Week 06–07 เราเก็บ `requesterName` เป็นข้อความในทุกคำร้อง
อธิบายว่าวิธีนั้นมีปัญหาอะไรบ้าง และการแยกตารางแก้ปัญหาเหล่านั้นอย่างไร
คำใบ้ — ลองตอบคำถามนี้: **"ถ้าสมชายเปลี่ยนชื่อ ต้องแก้กี่ที่"**
### ปัญหาของการเก็บข้อมูลแบบเดิม
* ถ้าจะเปลี่ยนชื่อสมชายจะต้องเปลี่ยนทุก requests ที่ เป็นสมชายทั้งหมด ถ้ามี  requests ที่เยอะขึ่้น จะทำให้การแปลี่ยน requesterName ยากและทำให้เกิดข้อผิดพลาดได้
### การแยกตารางแก้ปัญหาเหล่านั้นอย่าง
* หากนายสมชายเปลี่ยนชื่อ เราจะแก้ไขชื่อในตาราง users แค่ 1 ที่เท่านั้น ตาม id ของสมชาย
* ลดความซ้ำซ้อนตาราง requests เก็บแค่ id ผู้ใช้งาน

## 3. รายละเอียดตาราง

##ทำเป็นตาราง — คอลัมน์ · ชนิด · ข้อกำหนด · **เหตุผลที่เลือกแบบนั้น**
* เหตุผลสำคัญกว่ารายการ เพราะแสดงว่าคุณคิดมาแล้ว ไม่ได้ลอกมา
### users
| คอลัมน์ | ชนิด (Type) | ข้อกำหนด | เหตุผลที่เลือกแบบนั้น |
| :--- | :--- | :--- | :--- |
| id| INTEGER | PRIMARY KEY | เพื่อใช้เป็นรหัสระบุผู้ใช้ที่ไม่ซ้ำกัน ระบบสร้างให้อัตโนมัติ  |
| name | TEXT | NOT NULL | เพื่อระบุชื่อนามสกุลของผู้ใช้งาน |
| department | TEXT | NOT NULL | เพื่อระบุสาขา |
| email | TEXT | UNIQUE | เพื่อระบุอีเมลสำหรับติดต่อหรือเข้าสู่ระบบและป้องกันไม่ให้ใช้อีเมลซ้ำกันในระบบ |
###  requests
| คอลัมน์ | ชนิด (Type) | ข้อกำหนด | เหตุผลที่เลือกแบบนั้น |
| :--- | :--- | :--- | :--- |
| id | TEXT | PRIMARY KEY | ใช้เป็นรหัสอ้างอิงหลักของคำขอ  |
| requester_id | INTEGER | FOREIGN KEY, NOT NULL | โยงไปยังตารางผู้ใช้งาน เพื่อระบุว่าใครเป็นผู้ส่งคำขอ |
| request_type | TEXT | NOT NULL | ระบุประเภทของคำขอ |
| location | TEXT | NOT NULL  | เก็บข้อมูลสถานที่ |
| details | TEXT | NOT NULL | เก็บรายละเอียด|
| priority | TEXT | NOT NULL  | กำหนดระดับความสำคัญของคำขอ |
| status | TEXT | NOT NULL | ติดตามสถานะการดำเนินงาน เช่น Pending, In Progress, Completed|
| created_at | TEXT | NOT NULL | บันทึกวันและเวลาที่สร้างคำขอ |
| updated_by | INTEGER | FOREIGN KEY | เชื่อมโยงไปยังตารางผู้ใช้งาน เพื่อระบุว่าใครเป็นผู้อัปเดตรายการล่าสุด |
| updated_at | TEXT | NOT NULL | บันทึกวันและเวลาที่มีการแก้ไขหรืออัปเดตข้อมูลล่าสุด |

## 4. เหตุผลของการเลือกชนิดและข้อกำหนด

## - ทำไม `users.id` กับ `requests.id` ใช้ชนิดต่างกัน
### users.id ใช้ INTEGER เพราะง่ายต่อการสร้าง เป็นข้อมูลที่เพิ่มแค่ตัวแรกที่ละ 1 และประหยัดพื้นที่เก็บข้อมูล ทำให้เชื่อมกับForeign Key ได้ง่าย
### requests.id ใช้ text ทำให้ user ที่ใช้เข้าใจง่ายเช่น REQ-01

## ทำไมต้องมี CHECK constraint ทั้งที่ API ก็ตรวจข้อมูลอยู่แล้ว
### ป้องกัน Data Corruption จากทางอื่น ข้อมูลไม่ได้ถูกสร้างหรือแก้ไขผ่าน API เพียงทางเดียว

## 5. ตัวอย่างการใช้ JOIN

> ใส่คำสั่ง SQL จริงและตารางผลลัพธ์ที่ได้
```sql
SELECT r.id, u.name, r.details , u.department
FROM requests r
JOIN users u ON u.id = r.requester_id
WHERE u.department = 'วิศวกรรมซอฟต์แวร์'
ORDER BY r.id;
```
### ตารางผลลัพธ์ที่ได้

| id | name | details | department |
| :--- | :--- | :--- | :--- |
| REQ-001 | สมชาย ใจดี | เครื่องปรับอากาศไม่ทำงานตั้ง... | วิศวกรรมซอฟต์แวร์ |
| REQ-002 | สุภาวดี รักเรียน | เข้าสู่ระบบห้องปฏิบัติการไม่ได้ | วิศวกรรมซอฟต์แวร์ |
| REQ-004 | สมชาย ใจดี | คอมพิวเตอร์เครื่องที่ 5 เปิดไม่... | วิศวกรรมซอฟต์แวร์ |
| REQ-006 | สุภาวดี รักเรียน | ขอยืมจอคอม | วิศวกรรมซอฟต์แวร์ |
| REQ-008 | สมชาย ใจดี | ขอยืมจอคอม | วิศวกรรมซอฟต์แวร์ |
